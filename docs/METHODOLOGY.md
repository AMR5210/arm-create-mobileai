# Methodology

What this project measures, and the rules the measurements follow. Code comments
referring to "Claim A" or "Claim B" mean the definitions below.

## The two claims

The project builds three variants of the same base model and measures them
side by side:

1. **`baseline-fp16`** — Qwen3-0.6B, unmodified.
2. **`ptq-2bit`** — the same model quantized to 2 bits post-hoc, with no training.
3. **`qat-2bit`** — the same model fine-tuned with 2-bit quantization simulated in
   the forward pass, then exported to the same runtime format as `ptq-2bit`.

Two separate claims are under test, and they are measured differently:

**Claim A — 2-bit versus fp16.** A memory and speed win. Either quantization
method delivers it, so it says nothing about QAT specifically.

**Claim B — 2-bit QAT versus 2-bit PTQ.** A quality win at the *same* bit width.
Speed and memory should be near-identical between the two, because both run
through the same runtime format and kernels (GGUF `Q2_K` via llama.cpp). Quality
is intended to be the only variable.

Claim B is the claim that matters, and the one that is easy to get wrong: any
difference in footprint between the two 2-bit variants is a confound, because a
variant carrying more precision can win on quality without QAT contributing
anything.

## Footprint parity between the 2-bit variants

Claim B requires the two 2-bit variants to be matched on disk, RAM and speed so
that quality is isolated. Parity is enforced in two places:

- `scripts/quantize_ptq.sh` quantizes the PTQ baseline with F16 tied embeddings,
  matching how the QAT exporter treats them. Without this the PTQ baseline carries
  a Q2_K embedding while QAT carries F16, which would credit QAT with an
  embedding-precision advantage it did not earn from training.
- `scripts/gguf_drop_tensor.py` removes the duplicate `output.weight` that
  `convert_hf_to_gguf.py` materializes, leaving both variants tied.

Both variants are therefore 310 tensors and 0.5960 B elements with identical
tensor names.

Measured parity is close but not exact: disk differs by 3.2% (479.8 MB against
495.2 MB) and peak RAM by 1.5%, because the QAT export holds 9 fake-quant
skip-layers at F16. Exact parity is available by giving PTQ the same precision
allocation, at the cost of weakening the baseline on 83 tensors; see
`results/wikitext2_perplexity.json` under `analysis.size_caveat`. Any report of
Claim B should state the residual difference rather than describe the footprints
as identical.

## Models and data

- **Base model:** Qwen3-0.6B.
- **QAT fine-tuning data:** a blend of an instruction set, WikiText-2 train, and
  general-domain FineWeb text. Blend ratios per run are recorded in
  `results/wikitext2_perplexity.json`.
- **Evaluation:** WikiText-2 test perplexity as the primary quality metric, with
  an off-domain C4 slice as a generalization check. `eval/data/` is generated by
  `scripts/prepare_eval_data.py`.

WikiText-2 is both a training-blend source and the primary eval corpus, on
different splits. There is no leakage, but the domains match, so a WikiText-2
gain partly reflects domain alignment. The C4 evaluation exists to separate the
two; see `results/c4_perplexity.json`.

## Hardware roles

These are fixed, and a figure measured on the wrong device is not a reportable
figure.

| Hardware | Role |
|---|---|
| **iPhone 17 Pro Max (A19 Pro)** | Primary benchmark device. All reported numbers come from here. |
| **Mac mini (M4)** | Development and validation only. Never a reported benchmark device. |
| **iPhone 12 (A14)** | Optional cross-generation comparison. Requires a separate framework build; see below. |
| **Cloud GPU (AMD MI300X)** | QAT fine-tuning. See `docs/AMD_ROCM_SETUP.md`. |

Simulator runs are development artifacts. They are written to
`results/dev-ios-sim/` and are untracked; `results/<tag>.json` holds device
figures only. Each record carries the SHA-256 of the model file it measured, and
its `device` field names the specific hardware.

## Disclosures

**KleidiAI ISA coverage differs across devices, and does not cover the 2-bit
path.** KleidiAI's accelerated matmul kernels depend on newer Arm ISA features
(dotprod, i8mm, SME). Its `supports_op` accepts `Q4_0`, `Q8_0`, `F32` and one
`F16` path — not `Q2_K`. Both 2-bit variants therefore run their weight matmuls
on stock ggml CPU kernels, with KleidiAI loaded but not dispatched. Any statement
about Arm acceleration should say which precision it applies to.

Separately, the framework is compiled for a fixed Arm baseline
(`armv8.6-a+dotprod+i8mm+fp16`), which requires A15 or newer. A build for the
iPhone 12's A14 needs `ARM_ARCH=armv8.2-a+dotprod+fp16`; running the default
build on A14 raises SIGILL. A cross-generation comparison would therefore reflect
both chip generation and differing kernel availability, not chip generation alone.

**No fp16 ceiling run.** Ratios against `fp16_raw` compare QAT to a model that
never saw the training blend, which conflates domain adaptation with the cost of
quantization. A fair ceiling — fp16 fine-tuned on the identical blend for the same
step count — has not been run. Until it exists, those ratios are raw data, not
support for an fp16 comparison in either direction.
